## Owner decision and outcome

The owner approved implementing item processing based on n8n, after reviewing
the explanation of NX-07. Ordinary list items should flow automatically to
the next node, without forcing a separate loop node. A first delivery is a
bounded, observable read-list → per-item action flow; do not claim full n8n
parity. Preserve workspace isolation and do not introduce V1/V2 node types.

## In scope

- Explicit item outputs for selected existing list operations, never heuristic
  splitting of arbitrary fields inside a JSON object.
- Safe, expression-capable access to the current item, following n8n's `$json`
  concept without evaluating arbitrary JavaScript.
- Execute downstream actions once per item; ensure an empty list performs no
  downstream action. Bound item counts and display per-item results.
- Persist enough state to distinguish each item's progress and failure, respect
  existing cancellation and ambiguous-write rules, and never auto-replay a
  potentially completed write. Cover expression, branching, item linking,
  concurrency, history, and worker interruption as supported by the delivery.
- Explicitly reject or clearly document unsupported graph patterns rather than
  silently process them incorrectly; preserve workflow records and credentials.
- Update product/architecture documentation and mock-based verification.
- Show execution status on the canvas: successful, failed, running, waiting
  and skipped nodes are distinguished by both color and accessible icon.
- Include the previously pending Google validation fix; one final verification
  and one `develop` → `main` PR after all authorized edits are complete.

## Out of scope

- Binary file storage, database change triggers, arbitrary graph cycles,
  unrestricted loop nodes, or new provider operations and OAuth scopes.
- Real provider calls or paid AI generation without separate authorization.
- The stopped `codex/nx-node-runtime-settings` worktree.

## Acceptance criteria

- [ ] A supported list → action workflow produces one action result per item,
  with distinct item expressions and a readable execution history.
- [ ] Zero items, limits, invalid inputs, item errors, cancellation and interrupted
  writes have deterministic and safe behavior, with no hidden mass replay.
- [ ] Unsupported item topologies cannot silently send wrong or duplicate data.
- [ ] Product, UI and tests accurately state the supported subset and its limits.
- [ ] Final `npm run verify` and CI pass before merge/deploy.
