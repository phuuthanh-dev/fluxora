# Google connector OAuth operations

Google connector credentials are workspace-owned and separate from Google login. Drive and Sheets share a connection and continue requesting the existing broad Drive and Sheets scopes. Gmail, Calendar and Chat have separate connection cards and request their own scopes. Google may return permissions combined with prior grants to the same OAuth client, even when Fluxora shows separate connection cards. Fluxora records the returned scopes in the encrypted credential and requires the scopes needed by that connection; separate cards do not promise isolated Google grants. Review the Google consent screen and Google's account permissions when managing access.

## State storage and deployment

Connector OAuth requires Redis even when the execution queue runs in another mode. `REDIS_URL` must point all API instances serving both authorization starts and callbacks to the **same** shared Redis database, with permission for `SET` with expiration and `NX` and the atomic Lua `EVAL` operation. The application uses `redis://localhost:6379` when `REDIS_URL` is unset. Instances also need the same configured `APP_ENCRYPTION_KEY` and Google OAuth client settings. The short-lived state record includes the PKCE verifier and a keyed browser/session binding, expires after ten minutes, and is consumed atomically. Protect Redis as sensitive internal infrastructure; do not expose it publicly or log its values.

If Redis cannot be reached, OAuth stops without saving a connection and the Connections page asks for the shared state service to be restored. A lost, expired, evicted, flushed or already consumed state requires a new authorization. Split Redis instances cannot safely support callbacks across API instances. Redis state is not a durable credential store and no database migration is required.

## Reconnect and legacy credentials

Reconnect targets one credential and verifies the old and new Google subjects before replacing tokens. Older credentials may not contain a subject. Fluxora attempts to obtain the subject only from the old access token. It never refreshes a legacy grant merely to probe identity, because a provider could rotate the refresh token before identity verification finishes. This only works when the existing access token can call Google's OpenID userinfo endpoint. If the old account cannot be verified, the owner reviews affected workflows and explicitly confirms the account selection before authorizing the existing connection again. Its credential ID remains unchanged. A known subject mismatch remains blocked; the owner must choose the original account. Email alone is not used as proof.

If a reconnected Gmail credential points to a different mailbox, the trigger stops when its mailbox checkpoint no longer matches. Review the trigger and explicitly reset or reactivate it as appropriate. Messages received during a gap may not be processed; reconcile that interval manually. Do not assume this operation replays missed messages.

## Granted-scope evidence

A successful connector callback records the actual returned scopes and the SHA-256 digest of that exact access token. The server also authenticates the scope evidence inside the encrypted credential, so user-supplied JSON on a manual connection cannot fabricate verified OAuth permissions. The proof is not returned to the browser or execution adapters. Existing credentials with neither scope field remain eligible for the Gmail candidate's legacy full-message read path, but not writes. Older credentials with scopes but without authenticated evidence are treated as legacy credentials: their claimed scope metadata is not trusted or exposed to scope-gated operations. Existing Google execution paths remain usable subject to Google’s actual permissions, and the Gmail candidate permits its legacy full-message reads but no scope-gated writes. Reconnect with explicit consent to enable new Gmail capabilities.

A refresh request does not include a `scope` parameter. In line with [RFC 6749 section 6](https://www.rfc-editor.org/rfc/rfc6749#section-6), when the refresh response omits `scope`, Fluxora reuses the original grant only if its recorded scopes are authenticated and bound to the refresh token used in that request. Explicitly returned, validated scopes describe the new access token and receive a new token binding. If those scopes are an exact subset of the verified original grant, that subset becomes a conservative authenticated baseline for a later omitted-scope response. An expansion or incomparable replacement cannot establish a safe new baseline: the current token uses the explicitly returned scopes, and the connection is flagged for reconnect before its next refresh. At expiry the API returns `GOOGLE_OAUTH_REFRESH_SCOPE_UNVERIFIED` without another provider call. Refresh-token rotation rebinds verified evidence to the replacement refresh token. Legacy credentials with no scope metadata continue on their legacy read-only path. Previously created scoped credentials without refresh-grant evidence continue as legacy credentials after refresh, regardless of whether Google returns scopes. Their scope metadata is discarded because the original grant cannot be established. Existing Google operations retain their prior behavior, including previously available Drive, Sheets, Calendar and Chat writes; these remain subject to Google’s own permissions, not a new local write gate. New Gmail scope-gated write operations remain unavailable until an explicit reconnect. The connection card identifies this legacy status and provides the reconnect action.

## Gmail capability consent

Gmail read access remains required for existing workflows. When creating or reconnecting a Gmail connection, the owner may explicitly select additional `send`, `compose`, `modify`, and `labels` capabilities. Only the selected scopes are requested alongside the existing read scope. Reconnect selects the existing credential and verifies the same Google account; users should retain all capabilities their workflows need. The selected set is bound to signed state and to the stored refresh token. Google may return a broader combined grant. The Gmail executor receives an effective projection for only the owner's selected capabilities, derived from the actual returned scopes. For example, Google `gmail.modify` or `https://mail.google.com/` can satisfy selected read access, but is projected to read-only unless broader capabilities were selected. A prior Google grant therefore does not silently enable an unselected operation. `gmail.modify` itself authorizes a broad set of mailbox operations, including compose/send and labels.

Google classifies `gmail.readonly`, `gmail.compose`, and `gmail.modify` as restricted, `gmail.send` as sensitive, and `gmail.labels` as non-sensitive. Public use can require Google OAuth verification; restricted data stored on servers can require a security assessment. Review the current [Google Gmail scope requirements](https://developers.google.com/workspace/gmail/api/auth/scopes) and configured consent screen. No approval or live qualification is implied.

## Concurrent refresh and provider behavior

Each refresh attempts a per-credential PostgreSQL transaction advisory lock without waiting inside the transaction. If another instance holds it, the contender releases its database connection, rereads the credential, and retries with bounded jittered backoff and a total deadline. Only the lock holder keeps a transaction open while contacting Google and saving the result. A compare-and-swap protects against a concurrent reconnect, and a failed refresh or lock wait rereads the current credential before failing.

**Deployment requirement:** stop and drain every old API, worker, scheduler, or other process that can refresh Google tokens, and wait for their in-flight provider requests to finish before starting the new refreshers. All new instances must use the same PostgreSQL database and locking code. A rolling deployment with old refreshers still active is unsafe because they do not acquire this lock; the lock cannot serialize requests from those processes. Deployment orchestration must enforce and verify this drain as a release gate before enabling traffic; the application cannot itself detect an old refresher.

The lock serializes ordinary concurrent refresh calls, but it cannot make Google's rotation and the local database commit atomic. A process crash, connection loss, or malformed provider response after Google rotates a refresh token can still leave the local grant stale and require reconnecting. No live-provider behavior or actual database-lock behavior is claimed by the synthetic tests.

Managed Google credentials use the same reference checks as other connections. Deletion is blocked when current workflow drafts or published versions, or active executions, refer to the connection. Graph references are stored in JSON; checks and concurrent graph/usage changes must be coordinated to guarantee this behavior under concurrent requests. Until that boundary is verified, do not delete a connection while workflow changes or retries are running.
