# Google Sheets tab and header discovery (NX-03)

This slice adds server-side, owner-scoped metadata discovery and an optional editor assistant. Existing spreadsheet selection, manual range entry, values matrix, saved graphs, and read/append/update execution remain available. The assistant changes a graph only when a user applies its preview.

## Discovery contract

With an authenticated workspace owner and a workspace-owned Google connection:

- `GET /workspaces/:workspaceId/credentials/:credentialId/google/sheets/tabs?spreadsheetId=...` lists at most 100 `{ id, title }` tab properties and sets `hasMore` if the provider returned more. Tabs are not paginated; manual entry remains necessary for further tabs.
- `GET /workspaces/:workspaceId/credentials/:credentialId/google/sheets/headers?spreadsheetId=...&sheet=...` explicitly reads formatted values from row 1, columns A through CV, and returns `{ headers: [{ column, name }], columnLimit: 100 }`. Columns are one-based, and blank and duplicate names are retained. Google can omit trailing empty cells. A header row may contain user data: clients should request it only after an explicit user action and should not log or cache it. The fixed limit does not establish whether more columns exist.

Both responses are non-cacheable. Spreadsheet IDs and tab names must be literal, bounded inputs; runtime expressions remain usable in the existing range and spreadsheet fields, but are not sent for discovery. Sheet titles are quoted and embedded apostrophes escaped in A1 notation. The service bounds the provider response to 1 MB, limits displayed tab count and header length, does not expose raw provider errors, and gives manual/expression fallback guidance on denial or discovery failure. Owner authorization precedes credential access; the existing credential reader may refresh an expired OAuth access token. Discovery permission does not guarantee write access or later access. Tab titles containing `{{` cannot currently be used for header discovery because expression-like input is rejected; manual ranges remain available.

Sheets metadata calls use the existing guarded outbound transport with manual, same-origin-only redirects and socket-level address checks. A cross-origin or blocked redirect returns the sanitized discovery-unavailable guidance; the bearer token is not sent to the redirect target. This change does not alter the existing Drive file-listing path.

The upstream APIs used are Google Sheets [spreadsheets.get](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/get) with a fields mask and [spreadsheets.values.get](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/get), with [A1 notation](https://developers.google.com/workspace/sheets/api/guides/concepts#a1_notation). These references were not fetched during this task.

## Editor assistant

Load tabs on request or enter a literal tab name, then preview the exact replacement range. Reading headers is a separate action that discloses the first-row read. The preview blocks save, publish, and run until applied or discarded, survives node selection changes, and becomes inapplicable if its workspace, credential, spreadsheet, operation, range, or matrix changes. A pending request is cancelled or ignored if its scope changes. For append only, an optional one-row mapping labels each value by its column and header, accepts expressions, retains blank positions, and previews the replacement matrix. Applying the preview atomically replaces the range and, when mapping was explicitly prepared, the whole values matrix; existing matrices are not converted implicitly. Read and update retain their existing values and execution behavior. The raw controls remain the manual and expression fallback.

For reads, the assistant previews `'<tab>'!A:CV`, covering all rows in the first 100 columns, including the header row; larger reads can hit the existing response-size limit. Append and update preview `'<tab>'!A1`. Applying can change a custom range, so the current and proposed range are both displayed. A mapped append can replace multiple rows or typed cells with one row of strings; the UI calls this out and requires the same explicit Apply. The header list does not track later changes in Google Sheets. Tab names containing `{{` cannot be used in the assistant; use the manual range field. Discovery denial does not prevent manual configuration.

The editor checks the synchronous pending-draft registry after saving and compares the current serialized graph with the exact graph sent to the server. If an edit remains staged or changes the serialized graph while the save is in flight, a chained publish, test run, or node debug stops. An earlier graph may already have been saved; the newer graph must be saved again. Node JSON and the Sheets preview cannot be applied over one another while either is pending.

## Further integration considerations

1. Keep the current range and matrix controls as the source of truth for every existing and new workflow. Merely opening an inspector, loading tabs, or selecting a spreadsheet must never modify the graph or request header contents.
2. When a literal spreadsheet and connection are selected, offer tab discovery. Present the existing range unchanged and offer manual range or expression entry on missing permissions, expressions, errors, or limits. Show the exact old and proposed ranges before an explicit Apply replaces a custom range. Recheck which spreadsheet and connection produced the preview before applying it.
3. On a separate explicit request, load row 1 for the selected tab. Display headers with column letters and positions, including blanks and duplicates. Tell users that row 1 is read and may contain data, that only the first 100 columns are inspected, and that headers may have changed since discovery. Do not treat names as unique keys or transform header values.
4. For append, provide a staged per-column mapping using the existing expression-capable value inputs. Preview the exact resulting matrix and target range; apply only on explicit confirmation, preserving selected column positions and empty gaps. Warn before replacing any existing matrix, and do not apply if the spreadsheet, tab, range, or matrix changed while the mapping was open. Do not shift columns based on header names, silently fill missing columns, change `USER_ENTERED`, or write a header row. Retain the raw matrix editor as fallback. Multi-row and non-string existing cells need lossless handling or must remain in the raw editor.
5. For read, show discovered column positions as informational labels and retain the provider-shaped output. Any future named output requires a separate opt-in contract that handles duplicate and empty headers without changing existing outputs.

Synthetic tests are included but were not run. Theme, accessibility, stale-request behavior, integration against the coordinator's complete branch, and live provider behavior still need verification. Runtime headers can be renamed or reordered after configuration; no discovery result guarantees a future write's intended columns.
