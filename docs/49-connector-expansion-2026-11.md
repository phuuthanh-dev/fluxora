# Connector expansion: Slack, Notion, GitLab and Jira

## Scope and evidence

This batch extends existing adapters rather than introducing another execution engine. It adds Slack thread replies and message updates, Notion paragraph append, GitLab issue update and pipeline/merge-request reads, and an initial Jira Cloud OAuth 3LO connector. Execute and retry guidance calls attention to uncertain external writes. See the task contract in `.agent/tasks/2026-11-10-connector-workflow-expansion.md` for the original scope and acceptance criteria.

Provider documentation and n8n references used for comparison:

- [n8n Slack node](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.slack/) · [Slack message threads](https://docs.slack.dev/reference/methods/chat.postmessage/) · [Slack update](https://docs.slack.dev/reference/methods/chat.update/).
- [n8n Notion node](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.notion/) · [Notion append children](https://developers.notion.com/reference/patch-block-children).
- [GitLab issues](https://docs.gitlab.com/api/issues/), [pipelines](https://docs.gitlab.com/api/pipelines/) and [merge requests](https://docs.gitlab.com/api/merge_requests/).
- [n8n Jira node](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.jira/) · [Atlassian OAuth 3LO](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/) · [Jira Cloud REST API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/).

The Jira slice uses the user's chosen Atlassian site and account. Tokens remain in the workspace vault; refresh uses a database lock to serialize rotation. Reconnect checks both site and account. Project and issue-type controls query the provider. Initial operations support issue creation (summary and optional plain-text description), reading, updating the summary, and adding a plain-text comment. Jira custom mandatory fields and subtasks are not supported by this slice; the provider can reject a create request when a project requires additional fields. Discovery lists up to 50 projects/types and allows an ID to be entered manually. Writes with uncertain outcomes require inspection at the destination before retry.

The app requests Atlassian's classic `read:jira-work` and `write:jira-work` scopes plus `read:me` and `offline_access`. Atlassian's write scope includes issue deletion even though the Fluxora actions above do not implement deletion. Each user must approve the app for their site. The Jira Developer app has these two Jira scopes, `read:me`, and the production/local callback URLs saved, but configuration of client credentials, app distribution, actual user consent and a real Jira site test remain separate provider-dependent steps. Atlassian requires apps storing personal data to use its [Personal Data Reporting API](https://developer.atlassian.com/cloud/jira/platform/user-privacy-developer-guide/) and respond to its erasure/refresh requests. The batch prepares a disabled reporting implementation, but data attribution and erasure remain incomplete. Do not attest compliance or enable public sharing. At preparation the site was unavailable; subsequently local OAuth and create/get/update succeeded on synthetic BTS-7. See docs/50 for current evidence. Do not claim the connector is production-qualified on the basis of mocks.

## Jira public-distribution blocker

Atlassian's distribution form requires a truthful confirmation of its Personal Data Reporting API when the app stores personal data. The Jira connection stores the authenticated account ID encrypted and execution history may contain issue summaries or other personal data supplied by users. The distribution form remains unsaved and the app remains `Not sharing`.

The disabled implementation records each authenticated Jira account in an encrypted ledger atomically with the connection, preserves its original timestamp on reconnect and retains it when a credential is deleted. It reports to the fixed 3LO endpoint with an app-owner bearer token, honours `Cycle-Period` (days; default seven), handles a definite 429 using `Retry-After`, and marks interrupted or uncertain requests for manual review. A `closed`/`updated` response becomes `ACTION_REQUIRED`; no data is automatically deleted. Admin-only `GET /api/v1/admin/jira-privacy-reporting` exposes aggregate statuses without account IDs. Reporting is off by default; `JIRA_PRIVACY_REPORTING_ENABLED=true` plus the workspace and credential IDs of the owner connection would activate it when the scheduler is enabled. Do not activate until the owner reviews the process and the remaining obligations below. A change of `APP_ENCRYPTION_KEY` needs a corresponding ledger migration: the ledger's keyed digest and encrypted ID depend on that key.

**Not complete:** this ledger tracks the authorizing account, not every person whose data may appear in arbitrary issue text or propagated workflow data. Existing execution/node/item inputs and outputs do not provide reliable per-person lineage. Credentials, workflow configuration, histories, logs, backups and information already sent to other services need an explicit attribution, retention and response plan. No automated erasure/refresh or operator resolution is implemented. A response requiring action cannot yet be resolved within Fluxora; request an owner review and design a safe process before activating reporting or sharing. Synthetic protocol tests are not evidence of Atlassian live qualification. An interrupted report is intentionally held as uncertain for operator intervention rather than potentially violating the provider's reporting cycle. Atlassian's requirements remain authoritative.
